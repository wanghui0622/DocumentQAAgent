## 二、作业目标（7 步闭环）逐项对照

作业要求系统围绕附件 PDF 完成以下闭环：

| # | 目标 | 实现状态 | 代码/证据 | 差距与风险 |
|---|------|----------|-----------|------------|
| 1 | **判断 PDF 类型并选择解析策略** | ⚠️ 部分完成 | `src/pdf/detector.py`：≥80% 低文本页 → `scanned`，否则 → `text_native`；`PdfPipeline` 分支选择 OCR 或 `TextExtractor` | **实际 GBT PDF 被判定为 `text_native`**（`data/processed/documents/GBT+1568-2008+键+技术条件/blocks.json`），走了 PyMuPDF 文本抽取而非 PaddleOCR。该 PDF 虽含文本层，但首页存在乱码（`犐犮犛`），与作业「扫描件、不可手工录入绕过」的意图不完全一致 |
| 2 | **提取正文、条款编号、表格信息** | ⚠️ 代码有、实际未走 OCR 结构化 | OCR 路径：`ClauseParser` + `TableParser`（`src/pdf/structurer.py`）；文本路径：整页 `paragraph` | **当前 blocks 全部为 `paragraph`，无 `clause`/`table` 类型**，条款 3.1、表1 以整页文本形式存在，结构化能力未在 GBT 文档上验证 |
| 3 | **构建可检索知识库** | ✅ 完成 | `SemanticChunker` + Chroma + BM25（`src/indexing/`）；多文档统一索引（`DocumentManager`） | 向量检索依赖 OpenAI 兼容 Embedding；DeepSeek 等无 embedding 时自动降级 BM25-only（`retriever.py` L50-74） |
| 4 | **接收问题、检索相关证据** | ✅ 完成 | `HybridRetriever`：0.4 BM25 + 0.6 Vector；表格/条款加权 | 金融文档部分问题检索分数低于阈值（0.35）导致误拒答 |
| 5 | **生成答案并返回来源页码/片段** | ⚠️ 功能有、评测未过 | `AnswerGenerator` 强制 JSON + citations；CLI/Streamlit 展示引用 | LLM 返回的 `doc_id` 常为 `GB/T1568—2008` 而非 `GBT+1568-2008+键+技术条件`，导致 **Citation Accuracy 评测失败**（见第四节） |
| 6 | **答案自检：依据/幻觉/拒答** | ✅ 完成 | `AnswerVerifier`：引用子串 + 数值 + LLM grounding 三重校验；`DocumentQAAgent` 多层拒答 | 花键无答案题拒答正确（规则 + 检索阈值）；自检逻辑在手动 ask 时可正常工作 |
| 7 | **测试方法与业务保障方案** | ⚠️ 文档完整、执行欠佳 | `doc/测试说明.md` + `tests/eval/`（10 题 golden QA）；`doc/设计说明.md` 扩展路线 | 缺少 OCR 错别字、模糊问题用例；无 pytest 单元测试；**eval 通过率 20%** |

## 三、核心任务与模块设计评估

### 3.1 已实现的模块链路

```
PDF → PdfTypeDetector → [OCR | TextExtract] → Structurer → Chunker
     → Chroma + BM25 → QueryRouter → HybridRetriever
     → AnswerGenerator → AnswerVerifier → QAResponse
```

| 模块 | 文件 | 职责 | 评价 |
|------|------|------|------|
| 解析层 | `src/pdf/` | 类型检测、PaddleOCR、条款/表格规则解析 | 设计合理；OCR 路径因检测阈值未在 GBT 上触发 |
| 索引层 | `src/indexing/` | 分块、Embedding、Chroma、BM25 混合检索 | 工程化良好，支持多 doc_id 过滤 |
| 问答层 | `src/agent/` | 路由、编排、生成、Verifier | 非简单套壳，有明确拒答策略 |
| 文档管理 | `src/documents/` | 注册表、多 PDF、统一索引 | 超出作业最低要求，体现扩展性 |
| 交互 | `src/cli.py` + `app/streamlit_app.py` | CLI 索引/问答/eval + Web 演示 | 满足「可复现、可体验」 |
| 插件协议 | `src/plugins/base.py` | `DocumentParser` Protocol | 仅有接口，无具体领域实现 |

### 3.2 设计取舍（与作业要求一致）

- **未用 MinerU**：OCR + bbox 聚类表格，4–6 小时可交付 → 已在 `doc/设计说明.md` 说明
- **混合检索**：BM25 补条款号/标准号精确匹配，向量补语义 → 合理
- **Verifier 依赖 LLM**：grounding 判断需 API → 有降级 fuzzy 匹配

### 3.3 未完成或仅停留在文档的部分

| 项目 | 文档声称 | 实际情况 |
|------|----------|----------|
| `config/domains/*.yaml` | 设计说明 §5 提及 | **目录不存在** |
| 领域 Parser 插件 | 设计说明 §5 | 仅 `base.py` Protocol |
| Reranker | 设计说明 §6「可加强」 | 未实现 |
| 演示视频 | 提交要求 + 演示说明 | **仓库内无 mp4/截图** |
| Q8 错别字题 | README 提及「拉面强度」 | **golden_qa 中无对应用例** |

## 四、面试官重点关注（6 项）对照

### 4.1 扫描 PDF、表格、OCR、检索、生成、自检等关键问题

| 关注点 | 覆盖情况 |
|--------|----------|
| 扫描 PDF | ⚠️ 检测逻辑有，但 GBT 附件实际走 text_native；OCR 代码存在但未在该 PDF 上验证 |
| 表格 | ⚠️ `TableParser` 已实现；当前 GBT blocks 中表1 为 page 级 paragraph 文本，非独立 table block |
| OCR 错误 | ⚠️ `OCR_CORRECTIONS` 纠错词典 + `fuzzy_contains`；**无自动化 OCR 错误测试用例** |
| 检索 | ✅ 混合检索 + 类型加权 + doc_id 隔离 |
| 生成 | ✅ Evidence-only prompt，JSON 结构化输出 |
| 自检/拒答 | ✅ 三重 Verifier + 多层拒答（无证据/幻觉/不足） |

**面试追问准备**：需能解释为何 GBT PDF 被判 text_native、若强制 OCR 结果如何、表1 如何从 paragraph 中答对。

### 4.2 Agent / RAG 流程设计（非简单套壳）

**优点**：
- `QueryRouter` 按表格/条款/超范围分类，影响检索权重与拒答
- `DocumentQAAgent` 编排完整 pipeline，非单次 retrieve+generate
- Verifier 独立于 Generator，可拦截幻觉

**局限**：
- 非多工具 Agent（无 ReAct、无外部工具调用链）
- 更准确的定位是 **「带路由与自检的 RAG 流水线」**，建议在面试中主动界定 scope

## 六、关键风险清单（提交/面试前）

### P0 — 建议在提交前处理

1. **演示材料缺失**：作业硬性要求，需录制或截图
2. **Citation doc_id 不一致**：在 `AnswerGenerator` prompt 中强制使用 evidence metadata 的 `doc_id`，或在 eval 中放宽匹配
3. **GBT PDF 未走 OCR 结构化路径**：考虑降低 `PDF_TEXT_THRESHOLD`、检测乱码率、或提供 `--force-ocr` 选项
4. **金融文档检索误拒**：调低阈值或改进 BM25 对长数字/表格文本的分词

6. **OCR/模糊问题测试缺失**：README 提到 Q8 但评测集无对应用例
7. **Agent 定位**：明确为 RAG + Verifier 流水线，非多工具 Agent 框架

### P2 — 加分项（时间允许）

9. 增加 pytest 覆盖 detector、verifier、fuzzy_contains

## 八、提交前建议动作（优先级排序）

1. **录制演示**：按 `doc/演示说明.md` 完成 5–10 分钟视频或截图序列
